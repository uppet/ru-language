# 原生签名分析诊断与固定点检查

C 目标的 `check`／`build` 可加 `--native-analysis`。例如：

```sh
python ru check application.ru --allow-native --native-analysis
python ru build application.ru --allow-native --native-analysis -o application
```

每次原生签名分析在标准错误输出一行 JSON，包含是否完成、分析秒数、表达式步数、200000 步上限、模块数、签名数、函数分析次数、既有摘要缓存命中次数、每模块步数及每函数声明位置的分析次数。失败也输出已经累计的统计；不执行如程序或加载 DLL。标准输出及默认不带此选项的成功输出不变。无原生代码时没有原生分析记录。标准库裁剪可能触发第二次分析，两条记录各表示一次，不应将某条时间当整个编译耗时。

这些记录包含本机源码路径，不含源码正文或运行输入。模块步数按正在检查的表达式所属模块计数，函数次数是实际重新分析次数而非运行次数。时间只覆盖签名分析，不含解析、C 代码生成或宿主编译。失败位置只是预算耗尽处，并不证明该行是热点或根因。

## 此次实现的边界

既有实现已经拥有按依赖版本校验的函数摘要缓存、递归足迹检查和有界缓存。本轮不把它们计作新增功能，也没有去掉递归／候选值／复杂度保护。

实测剖析发现，固定点循环反复序列化整个模块图占主要分析耗时。所有抽象状态写入已推进单调变化代数；本轮改用代数未变作为固定点的充分条件，避免全图快照。代数变化可能只来自新建的不可达容器或签名登记，因此新判据可能多做保守迭代，绝不因少看一个依赖而提前停止。旧结构快照仍保留为开发差分 oracle。

这主要修复每步检查成本，不承诺降低所有程序的分析步数。大型应用仍可能触达默认 200000 步；此时仍拒绝编译，不自动抬限或静默切后端。

## 可复现对照

```sh
python tools/benchmark_native_analysis.py application.ru --output analysis-default.json
# 开发诊断专用：仅此工具的独立子进程使用较高预算，不修改产品默认值。
python tools/benchmark_native_analysis.py application.ru --diagnostic-step-limit 2000000 --output analysis-oracle.json
```

工具在同一模块图上交替运行旧结构快照和新代数判据，每组至少三次、每次独立进程。报告保留源码摘要、原始时间、进程峰值 RSS（Linux KiB）、成功／拒绝状态、步数和生成的 ABI thunk 摘要。只有两端都完成且 thunk 一致时，才能用该结果说明完整分析一致；两端同样耗尽预算只证明拒绝行为，不能算编译成功。不同平台或不同预算的秒数不能混算加速比。
