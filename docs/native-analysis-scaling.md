# 原生 ABI 分析的有界复用

本轮优化 `rulang/native_c.py` 的静态分析重复工作，帮助较大的模块图在原有预算内完成。既有的函数摘要、私有作用域判定、代数固定点和数值候选合并仍然保留；本轮在这些机制上增加表达式复用、首次调用的稳定性证明与字面量阵内容复用。

范围限于显式启用的 C 原生签名分析。没有新语法、新运行时接口或运行时缓存，不执行如程序、不加载 DLL，不改变 Windows x64 原生目标、ABI、原生授权或普通 C 的运行时行为。缓存仅属于一次 `NativeCPlan`，不会跨构建保留。

## 预算不变，减少真正重复的访问

原有保护保持不变：

- `MAX_ANALYSIS_STEPS = 200000`：表达式分析步数上限。
- `MAX_STATIC_ALTERNATIVES = 128`：静态候选上限及固定点迭代上限。
- `MAX_CALL_SUMMARIES = 4096`：函数调用摘要条目上限。
- `MAX_SUMMARY_FUNCTIONS = 256`：每份摘要的传递调用足迹上限。
- `MAX_SUMMARY_DEPENDENCIES = 256`：函数摘要依赖上限，也是私有名称读取证明的上限。
- 原生签名数量、未知 ABI 拒绝、捕获目标检查、递归限制、延迟回调复验和可变别名失效规则不变。

新增缓存也有边界：表达式摘要最多 16384 条，每条最多 256 个依赖；字面量阵内容最多 1024 条。超过容量会淘汰缓存，依赖或调用足迹不完整则不保存可复用摘要，不能截短证据后继续命中。这些是条目／依赖数量限制，不是进程内存字节配额。

每次非空表达式进入分析，包括缓存命中，仍先计 1 步并检查原有上限。命中只省去已经证明可复用的子表达式遍历，不把计步改成“不同 AST 节点数”。首次分析字面量阵仍逐个访问并计入所有元素，超大的初始数据表不能借缓存绕过预算。真正超限仍报错，不自动提高预算或改走其他后端。

## 表达式摘要与按名称依赖

表达式缓存以 AST 节点、词法环境和取引用模式为键，采用 LRU 淘汰。取函数引用与隐式调用必须是不同条目。适用节点包含调用、成员、索引、运算、转换、阵、切片、典、对象创建和函数引用；简单叶节点仍按原路径读取。

只有一次求值期间全局抽象状态代数未变化、依赖和调用足迹完整时，才保存表达式结果。命中前逐项核对依赖版本，并确认传递调用足迹与当前活动调用栈没有交集；命中后仍把证据传给外层分析，不能隐藏递归边或外部依赖。

表达式读取环境时记录“环境＋名称”的版本，而不是让同一环境内任意无关名称写入都使结果失效。沿查找链经过的缺失名称也必须记录：后来出现的局部绑定可能遮蔽原先读到的外层值。已有的保守遮蔽合并与捕获目标检查继续适用。

按名称记录不替代可变容器的所有者版本。阵、对象、捕获环境、模块以及传递可达的别名仍保留所需依赖；内容写入、未知调用造成的失效或可达关系增长，都不能被“名称没有重新绑定”掩盖。不同摘要层仍可保守保留整个环境依赖，不保证每次无关写入都能命中缓存。

## 首次调用的私有读取证明

原来的函数摘要只在整次函数体求值没有推进全局代数时保存。即使函数只初始化无法逃逸的局部绑定，也常需要再完整分析一次才能得到摘要。

现在保留原来的无变化路径，并增加一个充分条件：所有外部依赖的首次读取版本与结束状态一致，而且全部私有名称读取也保持稳定。私有环境仍须由既有语法扫描证明没有可保留该作用域的嵌套函数、匿名函数或方法；不能仅凭名称是“局部变量”就省略捕获依赖。

私有读取按名称保留首次看到的版本，包含尚不存在的绑定。先读后写、先缺失后绑定或读取证据超限，都不能证明首次调用可以直接复用。实参、返回值和可变所有者的依赖照常检查；创建局部环境或登记签名带来的代数变化，只有在完整证明成立后才不再强制额外分析一遍。

这份私有读取记录用于证明本次函数结果可复用，不能拿它删除外部依赖。调用摘要仍按函数和抽象实参上下文区分，并沿用 4096 条摘要与 256 个函数足迹的边界。

## 收敛循环的稳定见证

循环仍按原有固定点判据迭代，最多 128 次；没有跳过首次迭代，也没有把运行时次数当作静态收敛证明。

每轮单独记录依赖和返回值，再将所有轮次的证据合并。当最后一轮达到固定点，只有同时满足以下条件，才用最后一轮的私有名称读取作为循环的稳定见证：

1. 整个循环累计的依赖与调用足迹完整。
2. 最后一轮的私有读取证据完整。
3. 全部轮次合并后的返回候选，与最后一轮的返回候选相同。证明比较若超出候选上限，只放弃优化，不提前抛出错误；原有函数返回检查仍在正常位置执行。

替换的只有循环内部的私有读取证明。所有轮次的外部依赖、传递调用足迹和返回候选都保留，返回容器的可变所有者也要被观察。循环之前已经发生的读取不会被这份见证覆盖；早期轮次有不同返回结果时，也不能仅凭末轮稳定而缓存首次调用。

## 字面量阵仅共享不可变内容

当阵的直接元素全部是数、串、事实或空字面量时，首次正常求值后保存不可变的元素 tuple，后续分析同一 AST 时可复用。缓存满时淘汰最早保存的条目；淘汰只增加重复分析，不改变结果。

共享的是元素内容，不是可变的抽象阵所有者。原有“AST 节点＋环境”阵缓存继续决定所有者身份，不同调用上下文仍有独立所有者、版本和失效状态。同一上下文原有的保守合并也继续生效，不能用字面量缓存重新恢复已经未知的阵内容。

包含名称、调用、成员或嵌套阵的外层阵不进入这一内容缓存。嵌套阵可以分别复用自己的纯字面量元素，但每层可变所有者仍按环境分开。该机制不改变运行时阵的分配或引用语义，也不会跨上下文共享可变内层阵。

## 诊断与复验

已有的 `--native-analysis` JSON 统计增加 `expression_hits` 和 `literal_array_hits`，分别记录表达式摘要与字面量元素 tuple 的命中次数。`steps` 仍是实际收费的表达式访问次数，`function_evaluations` 仍是实际重分析函数体的次数；命中次数不代表运行时调用次数或程序执行加速。

```sh
python ru check application.ru --target c --allow-native --native-analysis
python -m unittest discover -s tests -p 'test_native_analysis_scaling.py' -v
python -m unittest discover -s tests -p 'test_native_c_plan.py' -v
python -m unittest discover -s tests -p 'test_native_analysis_profile.py' -v
python -m unittest discover -s tests -v
```

新增回归将正常缓存、关闭表达式／字面量缓存，以及同时关闭首次调用证明的保守路径作差分，比较签名、回调签名和生成的 ABI 跳板；拒绝用例比较诊断类别、文本与来源位置。另覆盖：

- 缺失绑定、后续遮蔽、捕获先读后写、未知逃逸和延迟回调变更。
- 阵与对象别名、可达关系增长、返回阵失效和跨上下文所有者隔离。
- 递归足迹传播、取引用模式、依赖超限、缓存淘汰及原 200000 步精确边界。
- 循环前读取、不同早期返回，以及字面量首次逐元素计步。
- 合成规模用例直接计数表达式体访问，确认减少实际遍历，而非只调整统计口径。

真实应用应固定源码及完整依赖图，在基线和候选编译器上分别运行默认预算，并用同一诊断预算完成基线 oracle 对照。Linux 上可使用已有工具：

```sh
# 在两个编译器检出目录分别执行，使用同一份 application.ru 与依赖图。
python tools/benchmark_native_analysis.py application.ru --repeats 3 --output analysis-default.json
# 仅开发诊断子进程提高预算，产品默认值保持 200000。
python tools/benchmark_native_analysis.py application.ru --repeats 3 --diagnostic-step-limit 2000000 --output analysis-oracle.json
```

该工具的 `structural`／`generation` 两组比较的是旧结构快照与代数固定点，并不自动切换本轮缓存；编译器优化的前后对照必须来自不同检出目录。两端都完成且签名、回调及 ABI 跳板一致，才能用于完整结果对照；同时拒绝不算构建成功。对比时间时使用相同平台、Python、源码、预算和固定点模式，独立进程至少三次，不将不同预算的秒数混成加速比。

分析时间不包含解析、C 代码生成或宿主编译，工具的峰值 RSS 则覆盖整个工作进程；静态分析通过也不等于 Windows ABI 或 GUI 实测通过。原始诊断含源码路径及模块位置，公开记录只保留经过检查的汇总，不直接提交本机日志。

### 固定应用对照

2026-11-05 固定 [ru_notepad 目录搜索候选 cb0339c3](https://github.com/uppet/ru_notepad/commit/cb0339c3a0b14c94449662bf70681072cee907fa)，与如言基线 `c3bb177c6a15e90821e5495cc74b0fdfc39b893a` 对照。完整依赖图为 42 个模块，77 个原生签名、2 个回调签名。

- 基线需要 338609 步；本轮候选为 193584 步，减少约 42.8%。候选独立使用原 200000 步默认值完成 CLI 检查和 C 源码生成；基线默认值仍拒绝，不能把诊断预算下的成功称为默认构建通过。
- Linux 独立子进程交替运行基线与候选各三次。为完成同一工作量对照，两端计时使用相同的 2000000 步开发诊断预算，未改产品默认。分析耗时中位数由 9.875 秒降至 5.837 秒，进程峰值 RSS 中位数由 65712 KiB 增至 89152 KiB，约增加 23 MiB。该内存换取重复工作减少的结果仅代表此固定样本，不保证其他项目同比例变化。
- 六次输入源码内容、签名顺序与 ABI 跳板一致。使用相同源码路径映射后，完整 C 输出均为 15208340 字节且逐字节一致；这不是实际 Windows C 编译或 GUI 运行证据。
- 29 项新增回归与 79 项既有分析器回归通过。Node 测试为 333 通过、13 跳过；33 个 C 示例以及 33 个 JavaScript 示例构建／语法检查通过。

完整回归与真实 Windows、LLVM、自举验收应以对应提交的 CI 终态为准。Windows 平台专用测试在 Linux 上的跳过不算通过；本轮编译器改动也不替代 ru_notepad 更新固定编译器后的实际构建验收。默认预算仍有边界，不能据此宣称所有更大的项目都能完成。

历史固定点优化的测量说明见[原生分析诊断](native-analysis-performance.md)；它与本轮缓存优化的验收记录应分别解读。
