# ru_notepad：未闭合围栏的增量算法对照

在上一轮密核优化之上加入有界解析检查点和后缀复用，真实 Windows 的 1 MB 未闭合围栏双撤销从 **15.140 s 降至 0.782 s**，中位数约快 **19.36 倍**，耗时下降约 94.8%。六个完整 GUI 进程全部通过原检查，共 72 个阶段；原 30 秒门槛、两次 Undo 共用的计时窗口、输入／绘制和结果检查均未改动。

候选目录为 `dist/ru-notepad-incremental-candidate`，EXE 和三份 DLL 须放在一起。没有替换原安装，没有提交、推送或运行远端 CI。本次也没有运行完整产品所有验收组；这是本机算法实验。

## 对照结果

两个版本都启用上一轮直接 LLVM 密核，普通应用仍使用 C 后端。本轮唯一变量是增量开关：相同源码、编译器、清单、资源及 DLL，生成 C 只有一个 `v_fact(0)` → `v_fact(1)` 字节差异，直接 LLVM 密核逐字节相同，见[构建对照证明](notepad-incremental-2026-10-22/build-pair-proof.json)。

每个版本三轮，顺序为关闭、开启、开启、关闭、关闭、开启；所有计时顺序执行，未与构建或语义测试并行。下表是完整 GUI 阶段耗时的中位数，包含原观察器和只读进程内存采样成本，并非纯扫描 CPU 时间。未绑核、清缓存，也没有足够样本推算 p95／p99。

| 1 MB 未闭合围栏 | 密核＋全量扫描 | 密核＋增量算法 |
| --- | ---: | ---: |
| 首次打开 | 15.704 s | 15.721 s |
| 插入字符 | 7.572 s | 0.525 s |
| 退格 | 7.583 s | 0.524 s |
| 连续两次 Undo | 15.140 s | 0.782 s |

双撤销三轮原始值：全量路径为 15.221、14.922、15.140 s；增量路径为 0.780、0.782、0.784 s。最后一个撤销修订的实际发布计数每轮均为 **100,002 → 104 行**，批量原生调用为 **1953 → 2 次**；计数是单个最终修订的值，不把它冒充两次撤销的合计。

100 KB 多行和 1 MB 单长行的双撤销分别为 2.187 → 2.225 s、3.321 → 3.353 s，基本持平。多行打开为 1.606 → 1.850 s，插入 1.120 → 1.318 s，退格 1.319 → 1.090 s；完整十二阶段的全部样本，包括变慢的观察，均保留在[汇总](notepad-incremental-2026-10-22/summary.json)及六份 `gui-*.json` 中。首次打开仍需完整扫描，这次没有改善。

## 算法与适用范围

实现仍是如言源码，未新增手写 C Markdown 解析器。扫描完成后，每个编辑器身份保留至多 128 个冻结检查点：初始点、首个可用的约 1 KB 边界，之后通常间隔至少 16 KB。检查点包含原策略 24 槽及有界标题栈、标记、前缀和尾部；不缓存整份文本或原生指针。数组分别复制，旧检查点不会随新扫描修改。

收到确切的单次插入／删除通知后，从编辑之前最近的安全点恢复。按照该编辑的 UTF-8 字节差平移旧边界，局部重算并发布其折叠范围。越过被编辑的物理行后，若全部解析状态与对应旧检查点一致，且不存在待定段落或未确认标题，就复用未变化的尾部及最终状态。字节位置独立平移，其他 23 槽（含嵌套数组）逐项比较。后缀未变由具体的编辑事件及所属文档修订证明，不依赖抽样或哈希碰撞假设。

本次发布优化省去了不变尾部的写入；局部重算范围内仍可能写入相同层级，尚未实现逐行新旧层级比较。64 行发布、1024 字节读取、原 UI 预算及文档身份／线程／修订检查均保留，缓存放在扫描状态之外。取消、关闭和遗忘会释放所属身份的缓存。

当前仅对前一修订已完成且无增减行的编辑尝试复用。扫描中再次编辑、通知不适用、长度／行数复核失败时回退全量；改变围栏、HTML、标题等结构后，状态若不收敛就继续扫描到末尾。没有按样本内容做特判，也没有为 Undo 保存任意历史版本快照。检查点数达到上限时不会无限增长；大文件或长期编辑的覆盖与缓存淘汰策略仍可完善。

## 正确性验证与失败记录

Linux 和真实 Windows 各自完成 **62 个文档修订、89,956 行折叠结果** 与固定 `d964ea9` 原策略全量重算的比较，包含围栏关闭／破坏、Setext 回溯标题、HTML、容器、Unicode、CRLF、空文档、两次 Undo 的文本修订及缓存别名检查；两平台 GC live 均为零。见 `policy-linux.json`、`policy-windows.json`。

真实 Scintilla／Lexilla 控件另有 **42 组**逐行折叠、可见性和完整文本对照，实际执行编辑与 Undo；覆盖非零检查点恢复、扫描未完成时再次编辑，以及文档身份缓存清理。见 `native-windows.json`。

首轮原型遗漏了“标题到段落结束才补写折叠标记”的依赖，多行插入虽然扫描结束但标题位错误，原 GUI 检查在 30 秒拒绝了它。该失败保留为 [rejected-deferred-heading.json](notepad-incremental-2026-10-22/rejected-deferred-heading.json)。最终版只在无待定段落、标题全已确认的边界复用，并保证被编辑行已重新发布；没有修改原检查来接受错误结果。

候选 EXE SHA-256：`57030f311f8d929c8009d0a72c86c44ffdee56e4ae1b6d46d64762a08efc0993`。六轮记录分别包含实际运行 EXE／DLL 的校验值，交付目录字节相同。构建收据的旧 `activation_ast_changes` 字段当时仅统计密开关；本轮增量开关的单字节差异以独立构建对照证明为准，工具已修正后续收据的计数。
