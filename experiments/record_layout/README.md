# 动态记录阵与四字节定长记录：对照实验

这是存储表示实验，不修改默认记录布局、语言语义或编译器优化。两端都从如源码经同一个 C 编译器生成：

- 动态端：普通 `形 记录`，四个 `数` 字段，每条记录作为对象保存到普通阵。
- 紧凑端：一个拥有者 `NativeMemory`，按每条记录四个连续 `u8` 字节编码；使用 `读字节`／`写字节` 检查边界。没有手写 C 热循环，也没有将内核时间冒充全程序时间。
- 两端相同输入值域（0..250）、相同初始化公式、相同多次加权扫描和总和。普通动态字段的完整语义比 `u8` 更宽，这不是可以普遍透明替换的布局。

本机是 Linux。紧凑端仅复用仓库已有 `test_native_c_runtime.portable_test_source` 的测试平台适配器，实际存储和成员操作仍是当前原生 runtime。它验证表示／分派成本，**不是生产 Linux 原生支持、Windows ABI 验收或真实应用提速证据**。本轮没有增加公开记录数组语法或 MI 写入能力。

## 复现

仓库根目录执行，使用已有 Python、GCC，不安装依赖：

```sh
python experiments/record_layout/verify.py > record-correctness.json
python experiments/record_layout/benchmark.py --count 100000 --scans 4 --repeats 3
```

默认产物在本目录 `results/`，包含两份如源码、原始生成 C、插入时钟的生成 C、可执行文件及 `report.json`。`--directory` 可选择独立输出目录。`--prepare-only` 只构建，不计时。

`verify.py` 用独立 Python 整数公式检验 1、17、250、251、252、4097 条记录，涵盖输入公式模数两侧和重复扫描。性能脚本每端先预热一次，再交替三轮；每次新进程，输出都须完全匹配 oracle。

计时使用生成 C 中插入的 `CLOCK_MONOTONIC` 标记，分列初始化与扫描。打印结果和关闭／GC 清理不计入这两个阶段，但包括在 whole-process wall time；后者也包括进程启动及极小的 C 测量父进程。RSS 是极小 C 测量父进程通过 Linux wait4 读取的目标子进程高水位（KiB），避免大 Python 构建进程的 fork 高水位污染，不能等同记录负载的精确字节数。两端不改变默认 GC 策略。报告保存源码／runtime 哈希、编译 flags、工具链版本和所有原始样本，不能跨平台混算比例。

## 决策原则

紧凑表示若只减少存储而逐字段通用成员分派更慢，就不修改普通记录默认语义；应先有真实消费者和经过验证的批量／密核读写路径。此实验不以编码后数据更小作为端到端提速的证据。

## 独立补充：三字段稠密记录稳定排序

`sort_benchmark.py` 补齐原计划的排序场景，不替换上面的四字节扫描证据。两端使用**完全相同的如源码自底向上归并排序**，只替换造存储、读字段和写字段的实现；均由当前如编译器生成 C，`gcc -std=c99 -O2`。没有 C 手写排序密核，也不调用两种不同的内建排序。

- 字段为起始偏移、长度、原始序号，各以非负 u32 值约束。起始偏移从 65536 开始，可跨越 16 位范围；长度从 256 开始，混合输入有 257 个重复键；序号等于原输入位置。按长度升序，等长时总取左侧，不把序号加入比较器，独立 oracle 因而能验证稳定性。
- 动态端预先创建两个普通阵及全部形对象，归并逐字段写入既有对象，不在每次复制时另造对象。紧凑端实际拥有两个 `NativeMemory` 缓冲，每条 12 字节，三个 little-endian u32；读写由如代码调用现有边界检查字节接口实现。没有用动态阵冒充紧凑存储，也不新增 runtime API。
- 输入上限 699050 条，使两个紧凑缓冲合计不超过 16 MiB。全部字段小于 2^32，校验乘积小于 2^53，因此普通数可精确表示。空输入仅在正确性测试中使用，原生缓冲不接受零长度，故每个保留最小 12 字节且不读取记录。
- 与扫描实验相同，Linux 使用 `portable_test_source` 测试适配器。这不是生产 Linux 原生 ABI 验收，也不是 Windows 或实际应用性能证据。逐字节编解码、边界检查、函数调用与通用成员分派均是此紧凑原型的真实成本，不能将结果泛化为原生结构体数组的性能。

复现（仓库根目录）：

```sh
mkdir -p experiments/record_layout/evidence
python experiments/record_layout/sort_verify.py > experiments/record_layout/evidence/sort-correctness.json
python experiments/record_layout/sort_benchmark.py --count 12000 --repeats 3 --directory /tmp/ru-record-sort-bench
```

`--prepare-only` 只构建不采样。`sort_verify.py` 对空、一条、逆序、全相等、已排序、混合重复键及 2 的幂／257 键周期边界，共 22 个表示／输入组合，将**每个输出字段**与独立 Python `sorted(..., key=length)` 精确比对；最大为 4097 条，验证全部排序内容与稳定性，不仅检查总和。另检查越界 count 被拒绝。性能运行以相同 oracle 的三个按位置加权模校验值逐进程验算；这不是无碰撞证明，因此与完整输出正确性测试分开报告。

性能每端预热一次，然后至少三对独立进程，次序为动态／紧凑、紧凑／动态、动态／紧凑。报告分列初始化、排序、整进程 wall time 及 Linux `wait4` 子进程高水位 RSS。初始化包括两个存储的分配、动态对象的预创建及输入填充；排序只含所有归并轮次。校验输出及关闭／GC 在这两个阶段之外，但在整进程时间之内。RSS 包含 runtime、分配器和代码页，不能当作纯记录字节数。测量父程序在计时前编译，未更改默认 GC 策略。

`report.json` 保存所有样本、源码及生成 C／插桩 C／可执行文件哈希、全部如编译器 Python 与 runtime 头文件哈希、测试适配器哈希、GCC／cc1／汇编器／链接器／Python 二进制哈希、具体编译命令、CPU 和平台。测量应与其他重负载分开；共享宿主仍有背景噪声。
